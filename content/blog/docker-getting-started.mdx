“在我的电脑上明明能运行”，往往意味着运行环境没有被完整交付。应用依赖的系统库、运行时版本、配置和启动方式，只要有一项不同，就可能在另一台机器上失败。

Docker 的做法是把应用及其运行环境制作成**镜像**，再从镜像启动相互隔离的**容器**。团队交付的不再是一份“请自行配置环境”的说明，而是一套可以重复创建的运行环境。

这篇文章不试图列完 Docker 的所有功能。我们沿着一条最短实践路线，依次完成：运行现成镜像、管理容器、持久化数据、构建自己的镜像，以及用 Docker Compose 启动多个服务。

## 先建立一张概念地图

初学 Docker，最容易混淆的是镜像和容器。可以先记住下面这组关系：

- **镜像（Image）**是只读模板，包含文件系统、依赖和默认启动命令。
- **容器（Container）**是镜像的一次运行实例，本质上仍是宿主机上的隔离进程。
- **仓库（Registry）**用于存取镜像，Docker Hub 是常见的公共镜像仓库。
- **Dockerfile**是一份构建镜像的配方。
- **卷（Volume）**用于保存不应随容器删除而消失的数据。
- **网络（Network）**让容器之间能够按名称通信。
- **Docker Compose**用一个 YAML 文件描述并管理一组相关容器。

同一个镜像可以创建许多容器，就像同一个类可以产生多个实例。删除容器不会自动删除镜像，删除容器也不应该导致数据库数据丢失——需要长期保留的数据应放进卷。

Docker 通常以客户端—服务端方式工作：终端里的 `docker` 命令是客户端，Docker daemon 负责构建镜像、创建容器和管理网络与存储。Docker Desktop 会在 macOS 和 Windows 上准备好这一整套环境。

## 安装并确认 Docker 可用

macOS 和 Windows 初学者可以安装 [Docker Desktop](https://docs.docker.com/desktop/)。Linux 可以安装 [Docker Engine](https://docs.docker.com/engine/install/)。安装完成后，先运行：

```bash
docker version
docker info
docker run --rm hello-world
```

`docker version` 会显示客户端与服务端版本；`docker info` 会显示当前 Docker 环境；最后一条命令会下载 `hello-world` 镜像、创建容器并输出欢迎信息。`--rm` 表示进程退出后自动删除这个容器。

如果只能看到 Client 信息，或者出现 `Cannot connect to the Docker daemon`，通常不是命令写错，而是 Docker Desktop 尚未启动，或者当前用户无权访问 Linux 上的 Docker daemon。

## 运行第一个真正的服务

用 Nginx 启动一个后台 Web 服务：

```bash
docker run --name web-demo -d -p 127.0.0.1:8080:80 nginx:alpine
```

浏览器打开 [http://localhost:8080](http://localhost:8080)，应该能看到 Nginx 欢迎页。第一次执行时，本地没有 `nginx:alpine`，Docker 会先从仓库拉取镜像，再创建容器。

把这条命令拆开看：

- `docker run`：从镜像**创建并启动一个新容器**。
- `--name web-demo`：给容器一个容易记住的名字。
- `-d`：在后台运行。
- `-p 127.0.0.1:8080:80`：把宿主机的 `8080` 端口映射到容器的 `80` 端口，并只绑定本机地址。
- `nginx:alpine`：镜像名是 `nginx`，标签是 `alpine`。

端口顺序始终是 `宿主机端口:容器端口`。`127.0.0.1` 会把访问范围限制在本机；直接写 `-p 8080:80` 通常会监听所有宿主机地址，开发时不要在不知情的情况下暴露数据库或管理端口。

## 查看、调试和管理容器

容器启动后，下面几条命令最常用：

```bash
# 只看正在运行的容器
docker ps

# 查看所有容器，包括已经停止的
docker ps -a

# 持续查看日志，Ctrl+C 只会退出日志跟踪
docker logs -f web-demo

# 在运行中的容器内启动一个 shell
docker exec -it web-demo sh

# 查看容器的完整配置与状态
docker inspect web-demo
```

`docker exec` 不会创建新容器，而是在现有容器中执行额外命令。精简镜像通常只有 `sh`，不一定安装了 `bash`。

容器生命周期可以用下面几条命令控制：

```bash
docker stop web-demo
docker start web-demo
docker restart web-demo
docker rm web-demo
```

`docker stop` 只停止容器，容器仍然存在，因此可以用 `docker start` 再次启动。`docker rm` 删除的是已经停止的容器；需要强制删除运行中的容器时可以用 `docker rm -f web-demo`，但日常操作优先正常停止，让应用有机会完成清理。

这里有一个非常关键的区别：

- `docker run nginx:alpine` 会创建一个**新的**容器。
- `docker start web-demo` 会重新启动一个**已有的**容器。

如果反复执行 `docker run`，看到多个停止的容器并不是 Docker 出错，而是每次都创建了新实例。

## 管理镜像

镜像和容器有各自独立的命令：

```bash
# 下载镜像，但不创建容器
docker pull nginx:alpine

# 查看本地镜像
docker image ls

# 查看镜像详情
docker image inspect nginx:alpine

# 删除不再使用的镜像
docker image rm nginx:alpine
```

一个完整镜像引用可以写成 `仓库地址/命名空间/名称:标签`。省略仓库地址时默认从 Docker Hub 拉取；省略标签时通常使用 `latest`。`latest` 只是一个普通标签，不等于“运行时永远自动更新”，也不能保证每次指向同一份内容。学习时可以使用它，生产环境更适合固定明确版本，要求完全可复现时还可以固定 digest。

## 容器会消失，重要数据不能跟着消失

容器有自己的可写层，但它适合临时运行状态，不适合保存数据库、上传文件等重要数据。删除容器后，这个可写层也会消失。

Docker 常用两种挂载方式：

- **命名卷**由 Docker 管理位置，适合数据库和需要长期保存的数据。
- **绑定挂载**把宿主机的某个路径映射进容器，适合开发时同步源码或配置文件。

先用命名卷验证数据持久化：

```bash
docker volume create demo-data

docker run --rm \
  --mount type=volume,source=demo-data,target=/data \
  alpine sh -c 'echo "hello, volume" > /data/message.txt'

docker run --rm \
  --mount type=volume,source=demo-data,target=/data \
  alpine cat /data/message.txt
```

第一个容器退出后已经被 `--rm` 删除，第二个容器仍能读到文件，说明数据保存在容器之外。查看和删除卷可以使用：

```bash
docker volume ls
docker volume inspect demo-data
docker volume rm demo-data
```

绑定挂载适合把当前目录作为静态网站交给 Nginx：

```bash
docker run --rm -d --name local-site \
  -p 127.0.0.1:8080:80 \
  --mount type=bind,source="$PWD",target=/usr/share/nginx/html,readonly \
  nginx:alpine
```

修改当前目录的文件后，容器会立即看到变化。`readonly` 可以避免容器反过来修改宿主机文件。绑定挂载依赖宿主机的真实路径，而命名卷更容易跨不同开发环境复用。

## 用 Dockerfile 构建自己的镜像

假设有一个 Node.js 项目，依赖已记录在 `package.json` 和 lockfile 中，入口是 `server.js`。可以在项目根目录创建下面的 `Dockerfile`：

```dockerfile title="Dockerfile"
FROM node:24-alpine

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production
EXPOSE 3000
USER node

CMD ["node", "server.js"]
```

每条指令的职责都很明确：

- `FROM` 选择基础镜像。
- `WORKDIR` 设置后续指令和容器启动后的工作目录。
- `COPY` 把构建上下文中的文件复制进镜像。
- `RUN` 在构建阶段执行命令并形成新的镜像层。
- `ENV` 设置默认环境变量。
- `EXPOSE` 记录应用监听的容器端口，但**不会自动发布端口**。
- `USER` 避免应用进程以 root 身份运行。
- `CMD` 定义容器默认启动命令；JSON 数组形式能更正确地接收停止信号。

先复制依赖清单再安装依赖，最后复制源码，是为了利用构建缓存。只修改业务代码时，依赖安装层通常可以复用。还应创建 `.dockerignore`，避免把无关或敏感文件发送到构建上下文：

```text title=".dockerignore"
node_modules
.git
.env*
npm-debug.log*
```

然后构建并运行镜像：

```bash
docker build -t hello-docker:1.0 .
docker run --rm -d --name hello-app -p 127.0.0.1:3000:3000 hello-docker:1.0
docker logs -f hello-app
```

`-t` 给镜像设置名称和标签，最后的 `.` 是构建上下文。Docker 只能在这个上下文中读取 `COPY` 所需的文件，因此不要随意把包含大量文件的上级目录作为构建上下文。

环境变量可以在运行时传入，例如 `docker run -e PORT=3000 ...`。密码、令牌和私钥不要写进 Dockerfile，也不要复制进镜像；镜像层会被缓存和分发，事后删除文件也不代表它从历史层中消失。

## 用 Docker Compose 管理多个服务

当应用需要数据库、缓存或消息队列时，把所有参数塞进多条 `docker run` 命令很快会变得难以维护。Compose 可以把服务、网络和卷声明在一个 `compose.yaml` 中。

下面的示例会启动 WordPress 和 MySQL，适合在本机观察多容器协作：

```yaml title="compose.yaml"
services:
  wordpress:
    image: wordpress:latest
    ports:
      - "127.0.0.1:8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_USER: app
      WORDPRESS_DB_PASSWORD: dev-only-password
      WORDPRESS_DB_NAME: app
    depends_on:
      - db

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: app
      MYSQL_USER: app
      MYSQL_PASSWORD: dev-only-password
      MYSQL_RANDOM_ROOT_PASSWORD: "1"
    volumes:
      - db-data:/var/lib/mysql

volumes:
  db-data:
```

在 `compose.yaml` 所在目录运行：

```bash
# 创建并在后台启动全部服务
docker compose up -d

# 查看服务状态和日志
docker compose ps
docker compose logs -f

# 在指定服务的容器中执行命令
docker compose exec wordpress php --version

# 停止并删除容器和默认网络，保留命名卷
docker compose down
```

Compose 默认会为项目创建网络。`wordpress` 容器可以用服务名 `db` 访问数据库，所以配置写成 `db:3306`，而不是 `localhost:3306`。容器里的 `localhost` 指向容器自己，这是初学者最常遇到的网络误区之一。

`depends_on` 控制启动顺序，但不能保证数据库已经完成初始化。真实项目应为依赖服务配置 `healthcheck`，并让应用能够重试连接。

执行 `docker compose down -v` 会连声明的命名卷一起删除，示例中的数据库数据也会消失。先确认数据不再需要，再加 `-v`。

示例把密码直接写在文件里只是为了便于本地练习。实际项目应使用未提交到版本控制的环境文件、Compose secrets 或部署平台提供的密钥管理能力。

## 一张日常命令速查表

| 目的 | 命令 |
| --- | --- |
| 创建并启动容器 | `docker run [选项] 镜像` |
| 查看运行中的容器 | `docker ps` |
| 查看所有容器 | `docker ps -a` |
| 查看日志 | `docker logs -f 容器` |
| 在容器中执行命令 | `docker exec -it 容器 sh` |
| 停止 / 启动容器 | `docker stop 容器` / `docker start 容器` |
| 删除容器 | `docker rm 容器` |
| 查看镜像 | `docker image ls` |
| 构建镜像 | `docker build -t 名称:标签 .` |
| 查看卷 | `docker volume ls` |
| 启动 Compose 项目 | `docker compose up -d` |
| 查看 Compose 日志 | `docker compose logs -f` |
| 停止 Compose 项目 | `docker compose down` |
| 查看磁盘占用 | `docker system df` |

磁盘空间不足时，先用 `docker system df` 看清占用，再按需删除容器、镜像或卷。`docker system prune` 会批量清理未使用资源，不要把它当作无需确认的日常命令；尤其不要随意添加 `--volumes`。

## 初学时最值得记住的五件事

1. 镜像是模板，容器是运行实例；`run` 创建新实例，`start` 启动旧实例。
2. `-p` 的顺序是宿主机端口在前、容器端口在后；`EXPOSE` 本身不发布端口。
3. 容器应该可以随时重建，重要数据交给卷或外部存储。
4. 同一 Compose 网络中的服务用服务名通信；容器里的 `localhost` 只代表它自己。
5. Dockerfile、Compose 文件和明确的镜像版本应该进入版本控制，密钥不应该进入镜像或仓库。

掌握这些内容后，你已经不需要背诵更多命令。遇到问题时，按“容器是否在运行 → 日志说了什么 → 端口是否正确发布 → 挂载是否正确 → 服务名和网络是否正确”的顺序检查，通常就能定位大部分入门阶段的问题。
